# Restaurant presentation and design publishing

Tap2Serve keeps one functional application and backend. The Tap2Serve team owns
website appearance; restaurant administrators retain menu/content, orders,
sessions, tax/service and other operational permissions. No restaurant designs
or assets are generated by AI. The included `tap2serve-classic` implementation
adapts the existing shared presentation and provides the fallback.

## Super Admin workflow

1. Open `admin.<base-domain>`, find the restaurant and select **Manage design**.
2. Select a registered implementation. Configure colors, typography, logo,
   hero/background/gallery images, English/Arabic hero titles and reusable
   component options. Branding assets are existing HTTPS URLs; uploading files
   or purchasing stock assets is outside this change.
3. **Save draft**. This updates the private draft, not the public website.
4. **Preview saved draft**. Choose Website or Guest ordering, Mobile or Desktop,
   and English or Arabic. The iframe loads the same presentation components as
   the public app. Preview content is inert and contains no live table token,
   session capability, orders or mutation controls. Preview is a representation
   of public content, not a separate application or deployment.
5. **Publish saved draft** atomically promotes the saved draft and retains the
   previous published configuration. **Revert published design** swaps back to
   that previous configuration and resets the draft to it. Another revert swaps
   the two again. This is a bounded one-step rollback, not an unlimited history.

Unsaved changes disable preview/publish/revert so the preview and publish action
refer to the same saved draft. Each command carries `expectedVersion`; stale
editors return 409. Refresh/reopen the editor to review another editor's changes.
Saving/publishing/reverting records actor, time and platform audit events.

An iframe URL is not a shareable preview credential. `/design-preview` authorizes
the Super Admin on every request, requires the exact saved design version and is
available only on the admin origin (or the explicitly enabled local environment).
It returns 404 to other users/origins and displays an expired-preview message for
stale versions. Private pages/API responses use `private, no-store`.

## Internal developer registration

The modules are:

| Module | Responsibility |
| --- | --- |
| `lib/restaurant-designs/catalog.mjs` | Reviewed implementation IDs, names, descriptions and implementation-specific option validation |
| `lib/restaurant-designs/config.mjs` | Structured configuration validation, defaults, publication/version logic and safe resolution |
| `app/restaurant-designs/registry.tsx` | Static imports and the implementation registry |
| `app/restaurant-designs/types.ts` | Public-content props and reusable presentation-slot contracts |
| `app/restaurant-designs/classic.tsx` | Existing shared public website, guest shell, hero and menu card |
| `app/restaurant-designs/presentation.tsx` | Tenant-local theme variables and renderer selection with fallback |
| `app/design-editor.tsx` | Super Admin draft editor and private preview controls |

To register a team-authored design:

1. Add its components under `app/restaurant-designs/`. Use the `DesignProps`,
   `GuestLayoutProps` and `CardProps` contracts. Reuse Classic components when
   only some slots need different presentation.
2. Add a stable ID to `DESIGN_CATALOG`. Its `validateOptions(options)` must check
   a strict, bounded, JSON-only schema; Classic accepts only an empty object.
   Keep the ID stable across code releases. Do not accept HTML, CSS, JavaScript,
   module paths, arbitrary font URLs or remote component definitions as options.
3. Statically import and register the implementation under the same ID in
   `DESIGN_IMPLEMENTATIONS`:

   ```tsx
   'team-authored-id': {
     Site: TeamWebsite,
     GuestShell: TeamGuestLayout,
     Hero: TeamHero,
     MenuCard: TeamMenuCard,
   }
   ```

   A guest layout composes these supplied React slots:

   ```tsx
   function TeamGuestLayout({header, content, navigation, floating, overlays}) {
     return <div>{header}<div>{content}</div>{floating}{navigation}{overlays}</div>;
   }
   ```

   Slots already contain the shared behavior and handlers. Do not reimplement
   ordering, billing, session transitions, capability handling or API clients in
   a design. Preserve the navigation, overlays, focus/accessibility behavior and
   disabled states when rearranging them. The content slot already contains a
   main landmark; keep any surrounding wrapper neutral.
4. Add tests for the implementation's rendering, mobile breakpoints, Arabic
   fallbacks, keyboard controls, RTL/LTR and options schema, then assign it from
   Super Admin. A code release registers the implementation once; assigning it
   to more restaurants requires only database writes.

The registry uses static code imports. Database values never become executable
imports or global style sheets. Missing/retired implementation IDs resolve to
Classic while retaining safe common branding. Malformed configurations use safe
defaults. Client render boundaries also preserve the Classic presentation if a
custom component fails after hydration; server-side custom code must pass its
render tests before registration. Removing code can prevent a configuration from
being published again until a registered design is selected, but does not take
down the public restaurant or shared ordering endpoints.

## Data and authorization

Per-restaurant `websiteDesign` holds `version`, `draft`, `published`, `previous`,
publication metadata and update metadata. In legacy mode it is part of the
existing CAS-protected `app_state` restaurant record. In normalized mode it maps
to `restaurants.website_design_json`, protected by the existing restaurant
revision/atomic D1 batch. Design publication never rewrites menu, order, session,
payment or table records. Unrelated tenants are not loaded for normalized edits.

The staged normalized model is now **version 3**. The design column is nullable
for untouched restaurants, which receive the default design. The automatic
deployment migration journal is unchanged. Rehearse the staged schema on a fresh
clone using [the D1 migration guide](D1_MIGRATION.md), or review an additive
upgrade from the prior staged model before any separately authorized cutover.
`CREATE TABLE IF NOT EXISTS` does not add a column to an existing table. Do not
mark an old database compatible without migrating/verifying it.

`GET /api/design?restaurant=<id>` is Super Admin only and returns the private
management document, public restaurant content and the registry catalog.
`platform.design.save`, `platform.design.publish` and `platform.design.revert`
go through the existing command authentication/CSRF pipeline and platform-owner
authorization. Hostname scoping rejects them on restaurant origins even for the
platform owner. Every design record is selected by the explicit restaurant ID
inside that authorized admin context; tenant-facing reads retain their existing
hostname scope.

Restaurant staff responses contain no design-management document or unpublished
configuration. Public/guest responses include only the resolved **published**
presentation config. Published colors/assets are inherently visible in a public
website; the security boundary prevents owners from editing them or seeing draft
state, previous configurations and private publication metadata. Their old logo
input was removed, and `settings.save` rejects visual-design fields server-side,
including direct forged requests from users with every restaurant permission.
Restaurant names, welcome text, menu item photographs and translated menu content
remain operational content; they do not grant layout/theme/branding controls.

## Styling and localization contract

Theme variables are scoped to `.restaurant-design`; dashboards and other tenants
are not given a shared mutable theme. The config accepts six-digit hex colors,
curated font stacks with Arabic fallbacks, bounded plain titles, and HTTPS asset
URLs without credentials or style-escape characters. Validation enforces readable
text/background contrast. Gallery images are bounded to six and implementation
options are schema-validated. CSS is mobile-first and uses logical spacing;
renderers receive localized content and `lang`/`dir` through the existing i18n
provider. A missing Arabic value falls back to the English/original value.

Client configuration cannot bypass tenant authorization. Internal design code is
trusted application code and must be reviewed accordingly: never fetch another
tenant, include secrets, write global tenant caches, use `dangerouslySetInnerHTML`
with content, or mutate operational data.

## Verification

```sh
npm test
npm run typecheck
npm run build
npm run test:tenant-worker
npm run test:normalized-worker
npm run test:auth-worker
```

Tests cover draft privacy, publish/revert/version conflicts, permissions including
forged legacy settings requests, invalid configurations/assets, independent
fallbacks, normalized persistence/concurrent writes, real Worker authorization,
private preview HTML, Arabic RTL, fallback rendering, unchanged guest ordering
and isolation across both storage modes. No tests deploy or contact live D1.
Interactive browser inspection depends on local browser access; automated HTML
checks do not replace visual and keyboard review of each future custom design.
